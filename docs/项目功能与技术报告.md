# 项目功能与技术报告

## 一、项目概述

本项目拟建设一个面向通用电商商品的评论 VOC 分析与产品改进决策系统。系统通过采集电商平台或真实数据环境中的用户评论，对评论文本进行清洗、UX 标签识别、情感分析、问题聚类、优先级评分、竞品对比、趋势分析和时间点前后对比，最终帮助产品负责人快速发现用户集中反馈的问题，并判断某个时间点前后用户反馈是否改善。

系统的核心目标不是简单展示评论列表，而是把大量零散评论转换为可理解、可排序、可追踪的产品决策信息。完整系统应形成如下闭环：

```text
商品链接 -> 商品绑定 UX 标签组合 -> 评论采集 -> 数据清洗 -> LLM/NLP 分析 -> 问题发现 -> 优先级排序 -> 竞品/趋势/前后对比 -> 产品改进决策
```

当前项目已经实现了基于真实评论数据的核心分析链路，包括真实评论导入、前端商品采集配置、商品级 UX 标签绑定、UX 标签识别、情感判断、问题优先级、正面卖点、竞品对比、趋势分析、词云展示和按时间点的前后 UX 标签变化对比。后端仍保留动作、旧验证和 showcase 接口用于兼容旧链路，但当前前端主看板只保留有后端计算数据支撑的业务组件。

## 二、系统建设目标

系统建设目标可以分为四类：

1. 评论洞察：从大量评论中识别用户关注的 UX 一级/二级标签，例如连接与稳定性、电池与续航、物流与包装、售后响应等。不同商品可以绑定不同标签组合。
2. 问题决策：根据负面率、提及量、趋势变化、竞品差距等指标计算问题优先级，帮助确定先改什么。
3. 改进判断：支持选择一个时间点，比较该时间点前后每个 UX 二级标签的提及量、负面率和改善率。
4. 验收展示：通过表格、趋势图、词云和对比面板，将分析结果以直观方式呈现。

## 三、完整功能设计与技术实现

### 1. 登录与访问控制

功能目标：限制系统访问，保证只有内部验收人员或授权用户可以进入看板。

前端呈现：登录页面，用户输入账号和密码后进入系统主界面。登录后显示左侧导航和各业务模块。

后端实现：完整版本应使用后端鉴权，例如 JWT、Session 或 Spring Security，登录成功后签发访问令牌，并在后续接口请求中校验用户身份。

当前实现：当前项目主要是前端门禁，通过环境变量配置账号和密码，由 Vue 前端完成校验。

技术选择理由：前端门禁适合演示和验收，开发成本低；正式系统应使用 Spring Security + JWT，因为安全性更高，也便于扩展角色权限。

### 2. 评论数据采集

功能目标：从电商平台、第三方 API 或手动导入文件中获取用户评论。

前端呈现：数据同步页面或同步状态卡片，展示同步来源、任务状态、抓取数量、失败原因和更新时间。

后端实现：完整版本应提供同步任务接口，支持外部 API 接入、分页抓取、失败重试、任务状态持久化和同步日志记录。当前项目已有 OneBound 同步任务骨架、`sync_jobs` 表，并新增 `POST /api/v1/reviews/import`，可把 Python 采集脚本输出的 JSONL 评论导入 `reviews_raw`。

当前实现：新增 `crawler/` 目录作为真实评论采集入口。参考京东采集仓库已下载在 `.tmp/external/Crawling-User-Reviews-from-JD.com`，当前项目自己的 `crawler/jd_reviews.py` 负责浏览器辅助采集和 JSONL 输出，`crawler/import_reviews.py` 负责导入后端。后端已删除旧的自动初始化入口，当前主线只接受真实采集脚本、第三方数据源或人工整理的真实评论。

技术选择理由：京东页面和接口可能变化，使用 DrissionPage 浏览器辅助采集可以在人工正常登录和合规访问前提下捕获评论数据；JSONL 方便断点续传、去重和后续 LLM 流水线处理；后端导入接口让真实评论进入现有数据库和分析看板。

### 3. 数据清洗与预处理

功能目标：将原始评论转换为适合分析的标准文本，减少脏数据对分析结果的影响。

前端呈现：当前通过数据质量接口提供原始评论数、清洗后评论数、删除数量、HTML 清理数量、精确重复数量、空评论数量和无效 JSON 数量；这些统计可用于解释数据来源质量。

后端实现：后端新增 `data_quality_runs` 表保存清洗摘要，`GET /api/v1/data-quality` 返回最近一次清洗统计。导入接口 `POST /api/v1/reviews/import` 支持可选 `cleaningSummary`，因此 Python 清洗脚本的结果可以跟导入批次关联起来。

当前实现：新增 `pipeline/clean_reviews.py`，输入 `crawler/output/raw_reviews.jsonl`，输出 `pipeline/output/cleaned_reviews.jsonl`、`removed_reviews.jsonl` 和 `cleaning_summary.json`。清洗只做保真处理：

- 删除无效 JSON 行。
- 删除 `content` 为空或去 HTML 后为空的评论。
- 删除精确重复评论，优先按 `source + sourceReviewId`，缺失时按 `productCode + content + reviewTime` 稳定哈希。
- 转换 HTML 标签、HTML 实体、零宽字符、异常换行和多余空白。
- 保留默认好评、短评论、低信息评论、普通中性评论和所有有效差评。

技术选择理由：当前采集阶段已经做过去重，新增清洗模块主要保证文本有效性和去除 HTML 技术噪声；不过度过滤默认好评和短评论，是为了避免改变真实 VOC 频率和情感分布。

### 4. UX 标签识别

功能目标：识别每条评论主要反馈的是哪个 UX 一级/二级标签。UX 一级标签表示大类，例如产品硬件、产品体验、服务与履约；UX 二级标签表示真正用于聚合和决策的细分问题，例如连接与稳定性、电池与续航、售后响应。

前端呈现：UX 二级标签会出现在问题列表、趋势图、词云、竞品对比表和正面卖点模块中。新增“采集配置”模块允许用户编辑商品的 UX 一级/二级标签组合，并把该标签体系绑定到当前商品。

后端与算法实现：当前后端新增 `ux_taxonomies`、`ux_primary_labels`、`ux_secondary_labels` 和 `product_taxonomy_bindings`，每个商品绑定一个 UX taxonomy。分析时后端把 taxonomy 传给 NLP 服务，NLP 服务要求 LLM 或本地规则输出固定 JSON，包括 `uxPrimaryLabel` 和 `uxSecondaryLabel`。完整版本可以采用“规则 + LLM + 人工配置”的混合方法：

- 第一层：UX 标签同义词词典，用于高置信度识别。
- 第二层：LLM 结构化判断，用于识别规则无法覆盖的表达。
- 第三层：前端可编辑 taxonomy，方便按商品和品类调整。

当前保留的 legacy aspect 包括：

- `battery`：续航、电池、充电、掉电。
- `bluetooth`：连接、断连、蓝牙、连接稳定性。
- `noise-canceling`：降噪、通透、noise canceling。
- `comfort`：佩戴、耳压、舒适。
- `microphone`：通话、麦克风、收音。

技术选择理由：固定 aspect 只能覆盖蓝牙耳机，无法支持所有商品；UX taxonomy 可以把标签配置从代码里移到数据里。旧 `aspect` 字段仍保留为兼容层，用于旧图表、旧动作和旧测试，新的主聚合维度是 `uxSecondaryLabel`。

### 5. 情感分析

功能目标：判断评论对某个方面的态度是正向、中性还是负向。

前端呈现：情感结果体现在负面率、趋势图、问题优先级、词云情绪标签和验证结果中。

后端与算法实现：当前 NLP 服务优先调用 OpenAI-compatible LLM，要求模型返回固定 JSON 字段，包括情感、方面、负面强度、UX 一级/二级标签、标准原因、置信度和证据。未配置 LLM、外部调用失败或返回结果不合法时，NLP 服务和后端都会回退到基于真实评论的本地规则分析。

完整版本可采用：

- 规则词典：适合明确的情感词。
- 评分辅助：低评分评论更可能是负向反馈。
- 机器学习模型：例如基于预训练中文模型的情感分类。
- 置信度机制：低置信度结果进入人工复核或降级展示。

技术选择理由：规则方法可解释、成本低；模型方法准确率更高。系统可以先用规则保证稳定，再逐步引入模型。

### 6. 问题聚类与优先级评分

功能目标：把零散负面评论聚合成产品问题，并计算哪些问题最值得优先处理。

前端呈现：问题列表或问题表格，展示问题标题、所属方面、优先级分数和证据摘要。

后端实现：后端将评论分析结果物化到 `review_aspects`、`review_semantic_labels`、`issue_clusters`、`issue_scores` 等表中，并根据固定权重计算问题优先级。`review_aspects` 和 `issue_clusters` 同时保存 legacy `aspect` 和新的 UX 标签，但问题聚合按 `uxSecondaryLabel` 进行。

当前评分因素包括：

- 负面率：该方面负向评论占比。
- 提及量：用户讨论该方面的频率。
- 趋势增长：最近负面反馈是否上升。
- 竞品差距：我方与竞品在该方面的差距。

当前权重设计为：

```text
priorityScore = 0.35 * negativeRate
              + 0.25 * mentionVolume
              + 0.20 * trendGrowth
              + 0.20 * competitorGap
```

技术选择理由：加权评分简单透明，适合答辩解释，也能让产品人员理解为什么某个问题排在前面。

### 7. 竞品对比

功能目标：比较本产品与竞品在不同 UX 二级标签上的用户反馈差异。

前端呈现：用户输入主商品和竞品的 `productCode`，对比表格展示每个 UX 二级标签的我方分数、竞品分数、差距、两边提及量和两边负面率。

后端实现：后端读取两个已分析商品的物化 UX 标签分析结果，按 `uxSecondaryLabel` 计算平均分、提及量、负面数和负面率，并返回 `ourScore`、`competitorScore`、`gap`、`ourMentionCount`、`competitorMentionCount`、`ourNegativeRate`、`competitorNegativeRate` 和 `negativeRateGap`。竞品对比不需要在前端配置竞品关系，只需要提供两个 `productCode`；如果两边绑定的 taxonomy 不一致，后端返回 `taxonomy-mismatch`。

技术选择理由：竞品对比可以把单纯的用户反馈转化为市场竞争视角，说明产品在哪些方面落后或领先。

### 8. 趋势分析

功能目标：观察某一问题是否随时间变严重或改善。

前端呈现：趋势图或趋势列表，展示按周聚合的负面率和提及量。

后端实现：后端读取评论时间和 UX 标签情感结果，按照 ISO 周进行聚合，计算每个周期的负面率和评论量。接口推荐传 `uxSecondaryLabel`，旧 `aspect` 参数仅用于兼容。

技术选择理由：趋势分析能支持“问题是否正在扩大”的判断，比单次统计更适合产品决策。

### 9. 词云与关键词分析

功能目标：展示用户评论中的高频关键词，辅助理解用户具体在说什么。

前端呈现：词云面板，关键词按照频率或权重调整大小，并显示情绪标签。

后端实现：当前后端从已物化评论范围内提取词元，统计频次、权重和情绪标签，最多返回一定数量的关键词。

完整版本应结合数据清洗、中文分词、停用词过滤和同义词归并。

技术选择理由：词云直观，适合展示用户声音，也能为问题摘要提供证据。

### 10. 正面卖点提炼

功能目标：系统不仅识别负面问题，也从正面评论中提炼用户认可的产品卖点。

前端呈现：新增“卖点”模块，展示 UX 标签、卖点名称、提及量、正面率、分数和代表评论。

后端实现：分析任务会把每条评论的方面、情感、UX 一级标签、UX 二级标签、标准原因、证据和置信度写入 `review_semantic_labels`。`GET /api/v1/positive-insights` 只从 `sentiment=POSITIVE` 且 `uxSecondaryLabel` 有效的评论中聚合，按 `uxSecondaryLabel + aspect` 形成高频卖点。

当前算法：不是新增复杂聚类算法，而是复用预置 UX 标签体系。排序公式为：

```text
score = mentionShare * 0.45 + positiveRate * 0.35 + avgConfidence * 0.20
```

技术选择理由：卖点和缺陷分析都可以先采用“预置标签 + 高频统计”的可解释方法。这样答辩时能清楚说明卖点来自真实正面评论，不会因为过滤默认好评而改变样本结构。

### 11. 改进行动管理（后端保留接口）

功能目标：针对某个高优先级问题登记产品改进行动。

前端呈现：当前前端主看板不再展示动作列表。该能力保留在后端接口和数据表中，主要用于兼容旧链路和后续扩展。

后端实现：后端通过 `improvement_actions` 表保存动作信息，包括商品、问题、动作名称、说明、状态和创建时间。

技术选择理由：如果系统只发现问题，没有后续动作，就无法形成闭环。动作管理让分析结果转化为产品改进计划。

### 12. 时间点前后对比

功能目标：比较某个时间点前后的用户反馈变化，判断该时间点前后各 UX 二级标签是否改善。该设计不要求记录“改动了哪个 UX 标签”，只记录时间点和窗口。

前端呈现：前后对比面板提供商品 `productCode`、时间点和时间间隔选择。默认时间间隔是前后一个月，也可以选择前后两周、前后三个月或自定义前后天数。结果表按 UX 二级标签展示前提及量、后提及量、前负面率、后负面率和改善率。

后端实现：后端新增 `ux_change_checkpoints` 保存时间点和窗口；`POST /api/v1/ux-change-comparisons` 保存时间点后，从物化评论中按 `review_time` 切分前后窗口，并对每个有效 `uxSecondaryLabel` 统计提及量、负面数、负面率、改善率、样本状态和总结文本。旧 `GET /api/v1/validation` 仍保留，但当前前端主看板改用新的时间点前后对比。

完整版本应支持：

- 前后窗口配置。
- 样本量不足提示。
- 显著性检验或置信区间。
- 自动生成更稳健的前后变化结论。

技术选择理由：按时间点切分比动作验证更轻量，也更符合当前数据结构。它可以在没有动作配置的情况下，直接回答“这个时间点前后，哪些 UX 标签变好了、哪些变差了”。

### 13. 报告生成

功能目标：将分析结果整理成可提交的产品报告。

前端呈现：当前前端主看板不再展示报告中心。完整版本可以支持报告预览、模块选择和导出。

后端实现：当前项目已有报告预览接口，完整版本应进一步支持 PDF、Word 或 Excel 导出，并记录报告生成历史。

技术选择理由：报告导出可以让系统结果进入实际汇报流程，也适合课程验收。

### 14. 运行态监控与演示面板

功能目标：展示系统各阶段是否正常运行。

前端呈现：当前前端主看板不再展示 showcase 运行态面板。完整版本可以展示流水线面板、智能体席位、可解释性面板、韧性运行态面板。

后端实现：后端从同步任务、分析任务、物化结果、动作和验证数据中合成运行态。

当前说明：这些 showcase 模块更适合演示系统链路和运行状态，不应被解释为完整的生产级监控系统。采集链路现在也会通过 `sync_jobs` 表记录 `browser-crawler` 任务和 handoff 状态。

技术选择理由：运行态面板能帮助验收人员理解系统流程，也能快速发现某个环节是否缺数据或失败。

## 四、完整系统架构

完整版本建议采用分层架构：

```text
表现层：Vue 前端看板
接口层：Spring Boot REST API
业务层：同步任务、分析任务、洞察查询、动作验证、报告生成
算法层：FastAPI NLP 服务、规则词典、情感模型、聚类模型
数据层：PostgreSQL、Redis、任务表、评论表、分析物化表
部署层：Docker Compose、生产 Nginx、环境变量配置
```

系统数据流如下：

```text
用户评论
  -> 数据采集
  -> 数据清洗
  -> 商品 UX 标签体系绑定
  -> UX 标签识别
  -> 情感分析
  -> 问题聚类
  -> 优先级评分
  -> 前端可视化
  -> 竞品分析/趋势图/词云
  -> 时间点前后对比
  -> 产品改进决策
```

## 五、核心数据表设计

完整系统中的核心数据表包括：

| 表名 | 作用 |
|---|---|
| `products` | 保存商品信息 |
| `competitors` | 预留商品与竞品关系；当前竞品对比主链路不依赖该表 |
| `reviews_raw` | 保存原始评论 |
| `review_aspects` | 保存每条评论的方面和情感结果 |
| `ux_taxonomies` | 保存 UX 标签体系头信息 |
| `ux_primary_labels` | 保存 UX 一级标签 |
| `ux_secondary_labels` | 保存 UX 二级标签、同义词和启用状态 |
| `product_taxonomy_bindings` | 保存商品与 UX 标签体系的绑定关系 |
| `review_semantic_labels` | 保存 UX 标签、标准原因、证据和负面强度 |
| `issue_clusters` | 保存聚合后的问题簇 |
| `issue_scores` | 保存问题优先级评分 |
| `data_quality_runs` | 保存清洗摘要 |
| `ux_change_checkpoints` | 保存前后对比时间点和前后窗口 |
| `improvement_actions` | 保存改进行动，当前后端兼容保留 |
| `validation_metrics` | 保存动作验证结果，当前后端兼容保留 |
| `sync_jobs` | 保存数据同步、浏览器采集和本地导入任务状态 |
| `analysis_jobs` | 保存分析任务状态 |

## 六、关键技术选择与理由

| 技术 | 用途 | 选择理由 |
|---|---|---|
| Vue 3 | 前端单页应用 | 组件化开发，适合看板系统 |

## 八、验收与测试设计

完整系统应从以下角度验收：

1. 功能验收：是否能完成数据采集、清洗、分析、问题/卖点/竞品/趋势/词云/前后对比展示。
2. 接口验收：核心接口是否返回稳定结构，错误状态是否明确。
3. 数据验收：评论入库、分析物化、问题评分、竞品对比和前后窗口计算是否正确。
4. 前端验收：各图表、表格、空态、错误态、降级态是否展示合理。
5. 算法验收：方面识别、情感判断、关键词提取是否符合样例预期。
6. 部署验收：Docker Compose 是否能启动完整服务。

## 九、项目总结

完整补齐后的系统应是一个通用电商评论分析与产品改进决策平台。它通过商品链接采集和清洗获得真实评论数据，通过商品绑定的 UX 标签体系与 LLM/NLP 分析识别用户反馈中的体验问题，通过优先级评分、竞品分析、趋势图、词云和时间点前后对比帮助用户判断改进顺序与改进效果。

从课程项目角度，本系统的价值在于把文本分析、后端接口、数据库持久化、前端可视化和产品决策流程结合起来。当前项目已经完成了基于真实评论数据的 MVP 链路，但要达到完整系统水平，还需要重点补齐真实数据采集、数据清洗、正式 NLP 能力、后端鉴权、异步任务和报告导出等能力。
