# 代码文档

本文只以当前仓库代码为事实来源，覆盖实际存在的模块、入口、依赖、默认行为、边界条件、异常处理、隐式逻辑、性能与安全注意点。

## 1. 仓库实际结构

### 1.0 根目录启动脚本
- 路径：`start-review-analyzer.bat`
- 作用：Windows 一键启动入口。脚本会检查并补齐 `.env`，调用 `docker compose up --build -d` 启动 PostgreSQL、Redis、NLP、后端和前端。
- 端口处理：默认前端端口是 `5175`。如果脚本检测到该端口已经有可访问前端在运行，会只启动后端、NLP、PostgreSQL 和 Redis，避免 Docker 前端容器因端口冲突启动失败。
- 健康检查：脚本会等待后端 `/api/v1/health`、NLP `/health` 和前端首页，最后自动打开前端看板。
- Crawler 边界：采集服务不随主项目一键启动，也不由该脚本管理；用户需要采集时单独启动。
- 边界：该脚本只负责本地开发和验收启动编排，不改变业务接口、数据库结构或分析算法。

### 1.1 backend
- 路径：`backend/`
- 技术栈：Spring Boot 3.3.3、Java 21、spring-web、spring-jdbc、spring-validation、PostgreSQL 驱动、测试用 H2。
- 入口：`backend/src/main/java/review/backend/BackendApplication.java`
- 作用：提供健康检查、同步任务、采集任务、UX 标签体系、分析任务、真实评论导入、洞察查询、竞品对比、前后对比，以及兼容保留的动作登记、旧验证和 showcase v1 运行态接口。
- 当前主线：商品绑定 UX 标签组合 -> 真实评论采集/导入 -> 分析任务同步执行并物化 -> 查询层按 UX 二级标签消费物化结果 -> 前端再用显式状态语义展示。
- 当前目录组织：
  - `review/backend/api/`：接口入口，也就是各个 Controller。
  - `review/backend/api/dto/`：请求体和响应体对象。
  - `review/backend/application/`：业务流程、外部服务客户端和分析编排。
  - `review/backend/data/`：数据库访问、物化结果读写和启动建表。
  - `review/backend/config/`：Spring 配置。
  - `review/backend/util/`：小型通用工具。

### 1.2 frontend
- 路径：`frontend/`
- 技术栈：Vue 3、TypeScript、Vite、Vitest、Axios、GSAP、@antv/g2plot。
- 入口：`frontend/src/main.ts`
- 作用：提供单页评论分析控制台，先经过内部访问门禁，再进入看板模块。

### 1.3 nlp-service
- 路径：`nlp-service/`
- 技术栈：Python 3.11、FastAPI、Uvicorn、Pydantic。
- 入口：`nlp-service/app/main.py`
- 作用：提供基于关键词规则的方面识别、情感识别、打分与聚类。

### 1.4 crawler
- 路径：`crawler/`
- 技术栈：Python、DrissionPage、requests、JSONL。
- 入口：
  - `crawler/jd_reviews.py`：浏览器辅助采集京东评论，输出 `crawler/output/raw_reviews.jsonl`。
  - `crawler/service.py`：轻量 FastAPI 采集服务，供后端 `/api/v1/crawl/start` 转发启动任务。
  - `crawler/import_reviews.py`：读取 JSONL 并调用后端 `POST /api/v1/reviews/import`，可携带 `pipeline/output/cleaning_summary.json`。
- 作用：补齐真实评论采集入口，让项目从“真实评论分析”升级为“真实电商评论导入分析”。
- 合规边界：不绕过验证码、不绕过登录风控、不做高频恶意请求；检测到验证或风控提示时停止并提示人工处理。

### 1.5 pipeline
- 路径：`pipeline/`
- 技术栈：Python、标准库 JSON/HTML/正则。
- 入口：`pipeline/clean_reviews.py`。
- 作用：对 `crawler/output/raw_reviews.jsonl` 做保真清洗，输出 `pipeline/output/cleaned_reviews.jsonl`、`removed_reviews.jsonl` 和 `cleaning_summary.json`。
- 当前规则：只移除无效 JSON、清理后为空的评论、精确重复评论；只转换 HTML 标签/实体、零宽字符、异常换行和多余空白。
- 明确不做：默认好评过滤、低信息量过滤、短评论过滤、相似文本去重、按评分或情感过滤。这样避免改变真实 VOC 频率。

### 1.6 infra
- 路径：`infra/db/init/001_init.sql`
- 作用：为 PostgreSQL 初始化核心表结构。
- 注意：后端还会在启动时通过 `PersistenceSchemaInitializer` 再次执行 `CREATE TABLE IF NOT EXISTS` 与补列逻辑。

## 2. backend 模块说明

### 2.1 配置与启动模块
- `config/WebConfig.java`：注册全局 CORS，`allowedOriginPatterns("*")`、允许 `GET/POST/PUT/DELETE/OPTIONS`、允许任意请求头、`allowCredentials(true)`。
- `src/main/resources/application.yml`：默认端口 `8080`，OneBound 基础配置来自环境变量。
- 关键注意：
  - CORS 当前仍是宽开放配置。
  - `allowCredentials(true)` 与通配来源同时出现，运行时行为取决于 Spring 对 `allowedOriginPatterns` 的处理；代码未额外收敛来源范围。

### 2.2 API 接口模块
- 目录：`backend/src/main/java/review/backend/api/`。
- 作用：接收前端 HTTP 请求，做参数入口和状态码返回；真正业务判断交给 `application/`。
- `HealthController`：固定返回 `UP` 与当前时间。
- `SyncController`：创建同步任务、按任务 ID 查询。
- `AnalysisController`：创建分析任务、按任务 ID 查询。
- `TaxonomyController`：创建/读取 UX 标签体系，并把商品绑定到某个 taxonomy。
- `CrawlController`：从商品链接创建后端采集任务，并查询采集状态。
- `ReviewImportController`：导入真实评论数据，请求体必须包含 `productCode` 和非空 `reviews`。
- `DataQualityController`：查询最近一次清洗摘要，读取 `data_quality_runs`。
- `PositiveInsightController`：查询正面卖点，读取正面评论的 UX 语义标签聚合结果。
- `IssueController`：查询问题列表，默认 `productCode=jd-100127936932`。
- `CompareController`：查询竞品对比，支持 `comparisonProductCode`，默认主产品 `jd-100127936932`。
- `TrendController`：查询趋势，默认 `productCode=jd-100127936932`、`aspect=battery`。
- `WordCloudController`：查询词云，默认 `productCode=jd-100127936932`、`aspect=all`。
- `UxChangeComparisonController`：记录前后对比时间点，并按每个 UX 二级标签计算时间点前后变化。
- `ActionController`：登记动作，并提供动作列表/详情读取；当前前端主看板不再展示。
- `ValidationController`：查询旧动作验证结果，可选 `actionId`；当前前端主看板改用前后对比。
- `ShowcaseController`：返回流水线、智能体席位、可解释性、韧性运行态、报告预览等 showcase v1 接口；当前前端主看板不再展示。

### 2.3 应用业务模块
- 目录：`backend/src/main/java/review/backend/application/`。
- 作用：承载数据流主流程，例如真实评论导入、采集任务转发、分析任务编排、查询聚合、前后对比计算和 showcase 兼容运行态合成。

#### 2.3.1 SyncJobService
- 默认新建任务状态会先持久化，再根据 provider/platform 进入实际终态。
- `provider=onebound` 时会立刻走 OneBound 抓取逻辑。
- 第二轨重点是同步透明度、原始评论持久化与 `analysisHandoffStatus` / `analysisHandoffNote` 准备度，不会自动并入首发主链路。
- 安全注意：错误消息会尝试把 `key=` 与 `secret=` 参数打码。

#### 2.3.2 OneBoundReviewClient
- 调用 OneBound 外部接口并解析评论返回。
- 必须提供 `ONEBOUND_API_KEY`；`ONEBOUND_API_SECRET` 为空时会退回使用 key。
- 请求路径形如 `/{platform}/item_review`。
- 响应计数从若干候选字段中统计数组长度：`items/comments/rateList/list`。
- 边界条件：若响应为空则返回 `0`；若检测到错误结构则抛出异常。

#### 2.3.2A ReviewImportService
- 负责 `POST /api/v1/reviews/import` 的业务逻辑。
- 输入是 Python 采集或人工整理的评论 JSON 数组。
- 主流程：
  1. 规范化 `provider/platform/productCode`
  2. 创建一条 `sync_jobs` 导入任务
  3. 将每条评论转换为 `ExternalRawReview`
  4. 调用 `ExternalReviewRawRepository.upsertReviews(...)`
  5. 若请求体携带 `cleaningSummary`，写入 `data_quality_runs`
  6. 将导入任务标记为 `SUCCEEDED`
  7. 返回 `READY_FOR_ANALYSIS`，提示下一步调用 `analysis/start`
- 隐式逻辑：
  - `sourceReviewId` 缺失时，后端会根据商品、内容和时间生成稳定哈希 ID。
  - `rating` 会限制在 `0-5`。
  - `category/skuInfo/source` 会进入 `fetch_metadata`，为后续 LLM 多品类分析保留上下文。
  - 清洗摘要不参与评论过滤或分析计算，只用于解释本次导入前的数据质量。

#### 2.3.3 AnalysisJobService
- 不再只是建一条 `QUEUED` 记录，而是承载当前唯一分析物化入口。
- 主流程：
  1. 规范化 `productCode`
  2. 获取当前商品绑定的 UX taxonomy；请求带 `taxonomyId` 时会先绑定到商品
  3. 创建 `QUEUED`
  4. 立刻转 `RUNNING`
  5. 加载真实评论
  6. 把 taxonomy 一起传给 `NlpReviewAnalysisClient`
  7. 构建分析结果并调用 `AnalysisMaterializationRepository.replaceOutputs(...)`
  8. 标记 `SUCCEEDED` 或 `FAILED`
- 复用语义：当前保守选择是每次启动都重新分析，避免新评论或 UX 标签版本变化后继续复用旧 aspect 结果。
- 降级语义：
  - NLP 调用失败、超时、不可用，或返回不合法 `jobId` / `reviewIndex` / aspect / `polarity` 时，会回退到 `localFallbackAnalysis(...)`
  - 回退后任务仍标记为 `SUCCEEDED`
  - 降级原因通过 `errorMessage` 传回，格式类似 `degraded:nlp_invalid_response:...`
- 失败语义：
  - 没有评论、物化替换异常等运行错误会标记 `FAILED`
  - 失败信息不会额外包装成新字段，仍写入 `errorMessage`
- 当前事实：analysis 仍是同步请求内执行，不存在独立队列消费者、异步回调或调度器。
- 新增事实：analysis 会同时写入 `review_aspects` 和 `review_semantic_labels`。两张表都保存 `ux_primary_label`、`ux_secondary_label`。`review_aspects.aspect` 仍保留旧接口兼容，但问题、趋势、词云、对比和卖点的主维度已经迁到 UX 二级标签。

#### 2.3.3A TaxonomyService
- 负责 UX 标签体系的业务逻辑。
- 主要能力：
  1. 懒创建默认通用 UX taxonomy。
  2. 创建新 taxonomy 或基于旧 taxonomy 创建下一版本。
  3. 把商品 `productCode` 绑定到指定 taxonomy。
  4. 把 taxonomy 转成 NLP `/analyze` 可消费的结构。
  5. 负责 UX 二级标签标准化和 legacy aspect 兼容映射。
- 设计原因：商品品类不同，固定蓝牙耳机 aspect 无法覆盖手机、家电、服饰等商品；taxonomy 让系统变成“每个商品绑定一套可编辑 UX 标签组合”。

#### 2.3.3B CrawlJobService
- 负责前端商品链接采集入口。
- 主流程：
  1. 接收 `productUrl`、`productCode`、`taxonomyId`。
  2. 推断平台和商品编码，例如京东链接推断为 `jd-{itemId}`。
  3. 绑定商品 taxonomy。
  4. 在 `sync_jobs` 创建一条 `browser-crawler` 任务。
  5. 尝试调用 Python `crawler.service` 的 `/crawl/start`。
  6. 查询任务时，如果存在外部 crawler job id，会刷新 crawler 最新状态。
- 状态语义：
  - `CRAWL_RUNNING`：crawler 正在采集。
  - `WAITING_FOR_MANUAL_ACTION`：需要人工处理登录、验证码或风控提示。
  - `READY_FOR_IMPORT`：JSONL 已采集完成，需要导入同一 `productCode`。
  - `READY_FOR_ANALYSIS`：导入接口完成后才进入分析就绪状态。
- 合规边界：后端只转发到正常浏览器采集服务，不实现验证码绕过、登录绕过或高频请求。

#### 2.3.4 NlpReviewAnalysisClient
- 调用 `NLP_BASE_URL + /analyze`，把 `jobId`、`productCode`、评论列表和当前商品 taxonomy 发给 `nlp-service`。
- 对返回结构做合同校验：
  - `jobId` 必须匹配
  - `reviewIndex` 必须落在源评论索引范围内
  - aspect 和 polarity 必须能被后端规范化接受
- 返回结果不是“硬失败或硬成功”二元，而是 `success + optional degradedMessage` 语义，供 `AnalysisJobService` 决定是否回退。
- `AspectSentiment` 的核心字段是 `uxPrimaryLabel`、`uxSecondaryLabel`、`standardizedReason`、`evidence`、`negativeIntensityScore`。旧的 `aspect` 合同仍保留，目的是保护已有 MVP 查询和旧前端字段。

#### 2.3.5 真实评论读取与本地回退
- 后端不再生成评论，分析任务只从 `reviews_raw` 读取已导入的真实评论。
- 若 `reviews_raw` 中找不到目标 `productCode` 的评论，`analysis/start` 会返回 `FAILED`，错误信息包含 `no reviews found for productCode=...`。
- NLP 服务不可用、超时或返回无效结构时，后端会基于这些真实评论执行本地规则回退。
- 本地回退只负责保底生成方面、情感和问题聚合，不能替代 LLM 语义诊断。

#### 2.3.6 ReviewAggregationService
- 仍是真实评论本地规则回退的基础层，也是 NLP 回退时的事实来源。
- 从 `reviews_raw` 读取评论，再根据评论文本推断方面、根据评分推断情感。
- 方面默认映射：
  - `battery`
  - `bluetooth`
  - `noise-canceling`
  - `comfort`
  - `microphone`
  - 无法识别时为 `unknown`
- 评分情感阈值：
  - `<=2.5` 负向
  - `<=3.5` 中性
  - `>3.5` 正向
- 隐式逻辑：方面归一化支持中英文别名，如“续航/电池”“连接/连接稳定性”“降噪”“佩戴/舒适度”“通话/收音”。

#### 2.3.7 InsightQueryService
- 查询侧现在以 `AnalysisMaterializationRepository` 为主数据源，不再把临时规则聚合当长期 compute-on-read 主实现。
- `dataQuality`：
  - 读取 `DataQualityRepository.findLatest(...)`
  - 返回原始条数、清洗后条数、删除条数、HTML 清理条数、精确重复条数、空内容条数和无效 JSON 条数
  - 该统计只解释数据质量，不改变分析口径
- `positiveInsights`：
  - 读取 `ReviewSemanticLabelRepository.findPositiveInsightAggregates(...)`
  - 只聚合 `sentiment_polarity=POSITIVE` 且有有效 `ux_secondary_label` 的评论
  - 按 `aspect + uxPrimaryLabel + uxSecondaryLabel` 聚合，输出卖点名称、提及量、正面率、分数和代表评论
  - 排序分数为 `mentionShare * 0.45 + positiveRate * 0.35 + avgConfidence * 0.20`
- `listIssues`：
  - 读取物化 `issue_clusters + issue_scores`
  - 问题主标题、证据摘要和 issueId 优先使用 `uxSecondaryLabel`
  - 返回 `IssueListResponse(items, state, notice)`
  - 无物化输出时显式 `empty`
- `compare`：
  - 读取两侧物化后的 UX 二级标签分数、提及量和负面率
  - 返回 `taxonomy-mismatch`、`missing-target`、`primary-unavailable`、`comparison-unavailable`、`success`、`error`
  - 主商品和竞品只需要两个 `productCode`，不读取前端竞品配置；两边绑定 taxonomy 不一致时直接返回 `taxonomy-mismatch`
  - 已不再返回静态 compare 数据，排序按物化写入顺序保留，避免中文标签自然排序造成漂移
- `trends`：
  - 读取物化后的 UX 标签结果，再按 ISO 周聚合负面率与提及量
  - `uxSecondaryLabel` 是推荐过滤参数，`aspect` 只做旧参数兼容
  - 返回 `success` / `empty` / `error`
- `wordCloud`：
  - 只在已物化的评论范围内做词元提取
  - 最多返回 24 个关键词
  - 当评论范围存在但提取不到关键词时返回 `degraded`
- `validation`：
  - 优先查持久化的 `validation_metrics`
  - 缺少快照时，优先按动作关联 issue 的 `uxSecondaryLabel` 从物化评论中筛选样本，再按动作时间窗或回退边界现场计算并回写
  - 旧 action 只有 aspect 时仍可回退到旧方面过滤
  - 无动作、动作不存在、样本不足、回退总结都走显式 `state + notice/summary` 语义
  - 当前前端主看板不再展示该模块；前端使用 `ux-change-comparisons` 做无需动作 ID 的时间点前后对比
- 性能注意：
  - `reviewsCache` 仅用于部分验证回算场景，TTL 为 10 分钟
  - 大多数聚合仍在应用层内存处理，未见批量预计算管线、分页或复杂缓存层

#### 2.3.8 ActionService
- 仍是 `ActionRepository` 的薄封装。
- 支持创建、按 ID 查询、查询全部、补写 launch context，服务于动作列表和验证窗口解析。
- 当前前端主看板不再展示动作模块，该服务保留用于后端兼容和后续扩展。

#### 2.3.8A UxChangeComparisonService
- 负责 `POST/GET /api/v1/ux-change-comparisons`。
- 主流程：
  1. 规范化 `productCode`。
  2. 解析时间点和窗口 preset。
  3. 将时间点与窗口写入 `ux_change_checkpoints`。
  4. 从物化评论中读取窗口范围内的 `review_time`、情感和 UX 标签。
  5. 按每个 `uxSecondaryLabel` 统计前后提及量、负面数、负面率、改善率和样本状态。
- 窗口语义：
  - 默认 `ONE_MONTH`：时间点前一个月和后一个月。
  - `TWO_WEEKS`：前后 14 天。
  - `THREE_MONTHS`：前三个月和后三个月。
  - `CUSTOM`：前端传 `customBeforeDays/customAfterDays`，后端限制在 `1-365` 天。
- 业务边界：不记录“改动了哪个 UX 标签”，只记录时间点，然后放出前后每个 UX 标签的变化。

#### 2.3.9 ShowcaseService
- 已不是固定演示占位返回，而是基于真实持久化状态和查询输出合成 showcase v1 视图。
- `pipeline()`：
  - 汇总最近 sync、analysis、materialization、actions、validation 状态
  - top-level `status` 为 `LIVE`、`DEGRADED` 或 `RUNTIME_UNAVAILABLE`
  - stage 级别可出现 `UNAVAILABLE`、`IDLE`、`QUEUED`、`RUNNING`、`SUCCEEDED`、`FAILED`、`DEGRADED`
- `agentArena()`：
  - 把真实子系统状态映射到 `sync-lane`、`analysis-lane`、`insight-lane`、`action-validation-lane`
  - `confidence` 取决于状态和是否有 backing data
- `explainability()`：
  - 始终返回 `LIVE`
  - 有 top issue 时展示当前物化权重拆解，否则展示固定权重配置
  - 明确不是模型 attribution
- `chaos()`：
  - 读取最近 sync / analysis / materialization 运行信号
  - 返回 `STABLE`、`DEGRADED`、`RUNTIME_UNAVAILABLE`
  - 这是运行态信号板，不是脚本化故障注入系统
- `reportPreview()`：
  - 汇总 `issues`、`compare`、`trends`、`actions`、`validation` 的当前结果生成预览段落
  - 如果关键子查询不是成功态，则整体标为 `DEGRADED`
- 公共语义：
  - `implemented` 现在固定为 `true`
  - `note` 是合同说明字段，包含 `v1-state`、`strategy`、`data-source`，不只是自由文案

### 2.4 数据访问模块
- 目录：`backend/src/main/java/review/backend/data/`。
- 作用：封装数据库表读写和启动时 schema 初始化；上层业务不直接拼接这些 SQL 细节。

#### 2.4.1 PersistenceSchemaInitializer
- 后端启动后自动执行建表和补列。
- 隐式逻辑：即使 PostgreSQL 已通过 `infra/db/init/001_init.sql` 初始化，应用仍会再次尝试确保表和字段存在。
- 新增表：
  - `data_quality_runs`：保存每次导入携带的清洗摘要。
  - `review_semantic_labels`：保存每条评论的 aspect、sentiment、UX 标签、标准原因、证据、置信度和负面强度。
  - `ux_taxonomies`、`ux_primary_labels`、`ux_secondary_labels`、`product_taxonomy_bindings`：保存可编辑 UX 标签体系和商品绑定关系。
  - `ux_change_checkpoints`：保存前后对比时间点、窗口 preset 和前后窗口边界。

#### 2.4.2 ProductRepository
- 若 `product_code` 不存在，会自动创建产品。
- 新建时 `product_name=product_code`，`brand=unknown`。
- 边界条件：并发插入时靠唯一键与 `DuplicateKeyException` 重试兜底。

#### 2.4.3 ExternalReviewRawRepository
- 真实评论为“先更新，后插入，冲突再更新”的 upsert 行为。
- 同时维护 `sync_jobs`。
- 幂等性：同一 `seed_key + product_code` 重复初始化不会无限新增评论，而是转为更新。

#### 2.4.4 AnalysisMaterializationRepository
- 当前查询主链路依赖的核心仓储。
- 负责：
  - 覆盖式写入 `review_aspects`、`review_semantic_labels`、`issue_clusters`、`issue_scores`
  - 查询 issue、compare、trend、wordcloud、validation、ux-change-comparisons 所需的物化视图
  - 判断某产品是否已有物化输出
  - 查询最新源评论更新时间
  - 查询 top issue 的权重拆解
- 语义重点：compare、issues、trends、wordcloud、ux-change-comparisons、validation 和部分 showcase 都以这里的物化状态为真相来源。新代码尽量读取 UX 二级标签；aspect 只保留旧数据兼容。

#### 2.4.4A TaxonomyRepository
- 负责 UX taxonomy 持久化。
- 表关系：
  - `ux_taxonomies` 保存标签体系头信息。
  - `ux_primary_labels` 保存 UX 一级标签。
  - `ux_secondary_labels` 保存 UX 二级标签、同义词、描述和启用状态。
  - `product_taxonomy_bindings` 保存商品和 taxonomy 的绑定关系。
- 版本策略：`PUT /taxonomies/{id}` 创建新版本，不直接覆盖旧版本。

#### 2.4.5 ReviewQueryRepository
- 仅按 `productCode` 查询评论，按时间和 ID 升序返回。

#### 2.4.6 ActionRepository
- `status` 统一持久化为 `PLANNED`。
- 如果时间字段为空，读取时会用 `Instant.now()` 兜底。
- 现在还承担验证上下文和 launch window 的部分读写支撑。

#### 2.4.7 ValidationMetricsRepository
- 持久化动作验证快照。
- 验证接口优先读取这里的最新快照，避免每次都重新切窗计算。

#### 2.4.8 SyncJobRepository / AnalysisJobRepository
- 两类任务均以自增主键作为 `jobId`。
- `AnalysisJobRepository` 现在支持 `markRunning`、`markSucceeded`、`markFailed` 与按产品查最近成功任务。
- 查询不存在或 ID 非数字时返回空，由控制器转换为 `404` 或空结果。

## 3. frontend 模块说明

### 3.1 启动与全局入口

### 3.2 应用壳层 App.vue

  - `VITE_INTERNAL_ACCESS_USERNAME`

  - `product-setup`

  - `wordcloud`
  - `ux-change-comparisons`

  - 不再把 `overview`、`actions`、`validation` 和 showcase 模块放进主侧边栏

### 3.3 状态处理与前端合同语义
- `resolveContractMessage(...)` 统一把 `empty`、`degraded`、`runtime-unavailable`、`disabled`、`timeout`、`error` 映射成前端提示。
- `applyIssueResponse`、`applyPositiveInsightResponse`、`applyTrendResponse`、`applyCompareResponse`、`applyWordCloudResponse`、`applyUxChangeHistory` 把后端合同对象落到页面状态。

  - `taxonomy-mismatch`
  - `missing-target`
  - `comparison-unavailable`
  - `primary-unavailable`
  - `error`
  这些不是通用 collection state。
- `ux-change-comparisons` 历史接口只返回时间点和窗口；如果第一条历史没有明细，前端会自动请求详情接口，再展示每个 UX 标签的前后变化。

### 3.4 登录与交互模块

#### 3.4.2 AnimatedCharacters.vue

  - 单击跳跃
  - 双击高亮
  - 密码显示/隐藏联动

### 3.5 业务展示模块
- `StatusCard.vue`：状态卡片。

#### 3.6.2 WordCloudPanel.vue

## 4. nlp-service 模块说明

### 4.1 main.py
- 定义 FastAPI 应用 `wh-nlp-service`。
- 提供 `/health` 与 `/analyze`。

### 4.2 analyzer.py
- 当前实现是 OpenAI-compatible LLM 优先、本地规则兜底。
- 如果设置了 `OPENAI_API_KEY` 和 `OPENAI_MODEL`，会调用兼容 `/chat/completions` 的 LLM 接口，并要求固定 JSON 结构。
- 如果未配置 LLM、测试环境、外部调用失败或输出无法解析，会回退到本地关键词规则。
- 方面关键词：
  - `battery`
  - `bluetooth`（关键词里兼容 `connectivity`）
  - `noise-canceling`（关键词里兼容 `noise_canceling`）
  - `comfort`
  - `microphone`（关键词里兼容 `call quality` / `call_quality`）
- 情感关键词：
  - 负向：`差/断开/噪音/卡顿/不稳/发热/一般/掉电/衰减`
  - 正向：`好/稳定/清晰/舒适/流畅/满意`
- 打分固定：负向 `-0.78`，正向 `0.82`，中性 `0`。
- 置信度规则：文本长度 `<8` 返回 `0.74`，否则 `0.88`。
- 聚类逻辑：只对负向方面做计数聚类，并按提及次数降序排序。
- 语义字段：本地规则和 LLM 解析都会输出 UX 一级标签、UX 二级标签、标准原因、证据和负面强度；当请求体带 taxonomy 时，prompt 和本地兜底都会优先使用这套标签。
- 与 backend 的关系：backend 接受这些 NLP 输出，并校验 `uxSecondaryLabel` 是否属于当前 taxonomy；`aspect` 只作为 legacy 字段保存，不能再作为新业务主维度。

### 4.3 schemas.py
- `AnalyzeRequest`：`jobId`、`productCode`、`reviews`、可选 `taxonomy`。
- `AnalyzeResponse`：`jobId`、`aspectSentiments`、`issueClusters`。

## 5. 数据与初始化顺序
- 开发/生产 compose 都先起 PostgreSQL，再起 Redis 与 NLP，再起 backend，最后起 frontend。
- PostgreSQL 初始化来源有两处：
  1. 容器启动挂载的 `infra/db/init/001_init.sql`
  2. backend 启动时的 `PersistenceSchemaInitializer`
- 当前首发主顺序是：
  1. `POST /api/v1/reviews/import`
  2. `POST /api/v1/analysis/start`
  3. 前端读取 issues / compare / trends / wordcloud / validation / showcase
- 外部来源第二轨可额外产生 `sync_jobs` 与 `reviews_raw` 数据，但不自动替代上述主顺序。

## 6. 关键限制与“无法从当前代码确认”
- 外部来源 / OneBound 仍是第二轨骨架，只能确认同步透明度、原始评论落库与 handoff 准备字段，无法确认何时会自动接入 analysis lane。
- analysis 任务虽然已同步执行并物化，但当前没有独立异步调度器、批处理编排器或自动重试器。
- 可解释性当前明确只是 `LIVE` 的固定权重拆解，不能当作模型归因系统。
- chaos 模块是真实运行态信号板，但前端是否显示仍受 `VITE_SHOW_CHAOS_MODULE` 控制；关闭时是产品策略隐藏，不是后端未实现。
- 报告中心当前只确认预览拼装，不确认真实导出、权限审批、外部投递链路。
- 无法从当前代码确认生产环境日志落盘、轮转、聚合、监控、告警、备份恢复策略。
